### 1. Tại sao cần tách `Service Interface` và `Service Impl`?
#### a. Design Pattern & Nguyên lý kiến trúc
- **Dependency Inversion Principle (Chữ D trong SOLID):** Module cấp cao (Controller) không nên phụ thuộc trực tiếp vào module cấp thấp (Service Impl), cả hai đều phải phụ thuộc vào sự trừu tượng (Interface).
- **Strategy Pattern / Factory Pattern:** Giúp hệ thống dễ dàng thay thế hoặc mở rộng thuật toán (ví dụ: đổi công thức tính giá thuê xe ngày lễ, đổi nhà cung cấp cổng thanh toán) mà không làm sửa đổi bất kỳ dòng code nào ở phía Controller.

#### b. Cơ chế AOP & Dynamic Proxy của Spring
- Khi khai báo `@Transactional`, `@PreAuthorize`, hoặc `@Scheduled`, Spring không gọi trực tiếp class thực tế mà sẽ bọc lấy Service bằng một lớp vỏ bảo vệ (**Dynamic Proxy**).
- Khi có Interface, Spring sẽ sử dụng **JDK Dynamic Proxy** (chuẩn native cực nhanh của máy ảo Java) thay vì phải dùng thư viện bytecode manipulation nặng hơn là CGLIB.

#### c. Câu hỏi thực tế: *"Nếu tạo `AuthServiceImplV2 implements AuthService`, Controller inject `AuthService` thì Spring biết inject thằng nào?"*
Controller chỉ khai báo duy nhất Interface:
```java
@RestController
@RequiredArgsConstructor
public class AuthController {
    private final AuthService authService; // Khai báo Interface, không sửa dòng này!
}
```
Khi xuất hiện cả `AuthServiceImpl` (V1) và `AuthServiceImplV2` (V2), Spring IoC Container hỗ trợ **3 cơ chế giải quyết xung đột Bean (Bean Resolution)** cực kỳ linh hoạt:
1. **Dùng `@Primary`:** Đánh dấu `@Primary` lên class `AuthServiceImplV2`. Spring sẽ tự động ưu tiên inject V2 vào mọi nơi cần `AuthService`.
2. **Dùng cấu hình động `@ConditionalOnProperty` (Khuyên dùng trong Microservices):**
   ```java
   @Service
   @ConditionalOnProperty(name = "app.auth.version", havingValue = "v2")
   public class AuthServiceImplV2 implements AuthService { ... }
   ```
   Chỉ cần sửa file `application.yml`: `app.auth.version: v2` là toàn bộ dự án tự động chuyển sang dùng bản mới mà không cần chạm vào code!
3. **Dùng `@Qualifier` hoặc Spring Profile:** Gắn nhãn bean theo môi trường (`@Profile("dev")` vs `@Profile("prod")`) hoặc `@Qualifier("authServiceImplV2")`.

#### d. Giá trị cho Dev & Dự án
- **Loose Coupling:** Controller không bị ràng buộc với cách cài đặt bên dưới.
- **Dễ viết Unit Test:** Dev dễ dàng dùng Mockito tạo Mock (`@Mock private AuthService authService;`) mà không cần nạp toàn bộ cấu hình nặng nề của DB hay thư viện bên thứ ba.

### 2. Dùng chung static method `ApiResponse.success()` có ảnh hưởng lẫn nhau giữa các Request/Thread không?
#### a. Phân biệt thuộc tính đối tượng và tên hàm
Trong [ApiResponse.java](file:///f:/backend-training/car-rental-saas/backend/src/main/java/com/carrental/car_rental_backend/common/dto/ApiResponse.java):
- Dòng 19: `private boolean success = true;` $\rightarrow$ Đây là **Instance Field (Thuộc tính đối tượng)**. Nó nằm trên vùng nhớ Heap riêng biệt của từng Object được sinh ra.
- Dòng 30: `public static <T> ApiResponse<T> success(T data)` $\rightarrow$ Đây là **Static Factory Method**. Chữ `success` ở đây **chỉ là tên của phương thức**, hoàn toàn độc lập với thuộc tính `boolean success`.

#### b. Bản chất bộ nhớ (Memory Model & Thread-Safety)
```
[ Request 1 của Luồng A ] ───> Gọi ApiResponse.success(dataA) ───> Tạo Object A trên Heap riêng
[ Request 2 của Luồng B ] ───> Gọi ApiResponse.success(dataB) ───> Tạo Object B trên Heap riêng
```
- Hàm `static` này là **Stateless (Không lưu giữ trạng thái nội tại)**. Nó không sử dụng bất kỳ biến `static` nào để ghi nhớ kết quả.
- Mỗi khi được gọi, câu lệnh `ApiResponse.<T>builder().data(data).build()` được thực thi, cấp phát một vùng nhớ độc lập trên Heap cho Thread đó.
- **Kết luận:** Hoàn toàn **Thread-Safe 100%**. Hàng nghìn người gọi đồng thời không bao giờ có chuyện ghi đè hay rò rỉ dữ liệu của nhau.

### 3. Hai hàm `repository.save()` liên tiếp chạy tuần tự hay bất đồng bộ?
#### a. Thứ tự thực thi
- Chạy **hoàn toàn TUẦN TỰ (Synchronous)** từ trên xuống dưới trên cùng một Thread của máy chủ Tomcat.

#### b. Cơ chế Hibernate Persistence Context (First-Level Cache)
- Khi gọi:
  ```java
  userRepository.save(userA);
  userRepository.save(userB);
  ```
- Hibernate **chưa lập tức bắn lệnh `INSERT` hoặc `UPDATE` xuống PostgreSQL ngay tại dòng code đó**.
- Hibernate đưa `userA` và `userB` vào trạng thái *Managed Entity* nằm trong vùng nhớ đệm **Persistence Context** (First-Level Cache).
- **Cơ chế Write-Behind:** Đến khi method kết thúc và Transaction chuẩn bị Commit (hoặc trước một câu lệnh SELECT cần dữ liệu mới), Hibernate mới tự động gom và thực hiện thao tác `Flush` (bắn toàn bộ câu SQL xuống DB trong cùng 1 lần).

### 4. Đào sâu `@Transactional` & Cách tối ưu hiệu năng máy chủ
#### a. Vòng đời của một `@Transactional`
Khi một hàm được gắn `@Transactional`, Spring AOP Proxy sẽ thực hiện chuỗi hành động:
1. Mượn 1 Database Connection từ HikariCP Connection Pool.
2. Thiết lập cờ `connection.setAutoCommit(false);`.
3. Mở Transaction.
4. Chạy logic Java bên trong hàm.
5. Nếu chạy xong không có lỗi $\rightarrow$ Gọi `connection.commit();`.
6. Nếu gặp `RuntimeException` $\rightarrow$ Gọi `connection.rollback();`.
7. **Trả Connection về cho HikariCP Pool** để phục vụ các request khác.

#### b. Các tham số sống còn của `@Transactional`
- **`readOnly = true`:**
  - Tắt hoàn toàn cơ chế *Dirty Checking* của Hibernate (giảm tải CPU và RAM vì Hibernate không cần lưu bản snapshot để so sánh xem object có bị sửa không).
  - Cho phép Database định tuyến query sang các Read-Replica Node để cân bằng tải.
- **`propagation` (Mức độ lan truyền):**
  - `REQUIRED` (Mặc định): Nếu đã có Transaction bên ngoài thì dùng chung, nếu chưa có thì mở mới.
  - `REQUIRES_NEW`: Luôn luôn tạm dừng Transaction hiện tại và mở 1 Transaction hoàn toàn mới độc lập (thường dùng khi ghi Log kiểm toán AuditLog hoặc bắn mã OTP mà muốn dù nghiệp vụ chính lỗi thì log vẫn phải được lưu).
- **`rollbackFor = Exception.class`:**
  - Mặc định Spring chỉ rollback khi gặp `RuntimeException` (Unchecked Exception). Nếu trong code bắn ra `Exception` hoặc `IOException` (Checked Exception), Transaction sẽ **không rollback**! Do đó luôn gắn `rollbackFor = Exception.class` để bảo đảm an toàn dữ liệu.

#### c. Kỹ thuật tối ưu "Rút ngắn Transaction" (Chống sập Connection Pool)
- **Sai lầm chết người:**
  ```java
  @Transactional
  public void createBooking(BookingRequest req) {
      // 1. Mở transaction (đã giữ chặt 1 connection của DB)
      // 2. Gọi API bên ngoài (Gửi Email xác nhận, quét OCR, gọi cổng thanh toán VNPAY) -> MẤT 3 GIÂY!
      // 3. Lưu vào DB
  }
  ```
  - Trong 3 giây chờ mạng bên ngoài, Connection bị giam cầm vô ích. Khi có 50 người cùng gọi, toàn bộ Connection của HikariCP bị cạn kiệt $\rightarrow$ Toàn bộ server bị treo cứng (**Connection Pool Starvation**)!
- **Quy tắc vàng:** **Tách biệt hoàn toàn việc gọi mạng bên ngoài ra khỏi Transaction**. Hãy gọi OCR / Email / Thanh toán xong xuôi, sau đó mới mở Transaction thật nhanh để ghi DB và nhả Connection ngay lập tức.

### 5. Chuẩn hóa viết code: `Optional` & Object Mapping
- **`Optional.isEmpty()` vs `Optional.isPresent()`:**
  - `isPresent()` (Java 8): Trả về `true` nếu có giá trị.
  - `isEmpty()` (Java 11): Trả về `true` nếu rỗng (`null`).
  - *Quy chuẩn:* Dùng `if (optionalUser.isEmpty())` thay vì viết dấu phủ định `if (!optionalUser.isPresent())` giúp code sáng sủa, loại bỏ bớt phủ định logic.
- **Sử dụng MapStruct thay vì Manual Setter:**
  - Viết hàng chục dòng `.setName()`, `.setPhone()` bằng tay rất dài dòng và dễ bỏ quên trường.
  - Sử dụng **MapStruct** để tự động sinh mã mapper lúc compile-time, tốc độ tương đương code tay nhưng sạch và an toàn hơn rất nhiều.

### 4. Tại sao cần Bảng lưu vết Token (`user_tokens`) hoặc Redis thay vì chỉ dựa vào `exp` của JWT?
Dù JWT đã có sẵn thuộc tính thời hạn hết hạn (`exp`), các hệ thống tài chính / doanh nghiệp vẫn bắt buộc phải có cơ chế lưu vết ở Database hoặc Redis vì:

1. **Khả năng Thu hồi Token tức thì (Immediate Revocation):**
   - JWT là Stateless (phi trạng thái). Một khi Server đã ký token có hạn 7 ngày, Server không có cách nào thu hồi nó trước 7 ngày nếu không lưu vết!
   - Khi Admin bấm **"Khóa tài khoản"** hoặc **"Đăng xuất khỏi mọi thiết bị"**, nếu không có danh sách đối chiếu trên server, hacker cầm token cũ vẫn gọi API bình thường.
2. **Cơ chế Phát hiện Trộm Token (Token Reuse Detection - Tiêu chuẩn OWASP):**
   - Mỗi lần dùng Refresh Token A để lấy cặp token mới, hệ thống cấp Refresh Token B và đánh dấu Refresh Token A là *Đã sử dụng (Revoked/Used)*.
   - Nếu Hacker lén copy được Refresh Token A và gửi lên server sau đó: Server tra cứu thấy Token A đã từng được sử dụng $\rightarrow$ Phát hiện ngay có kẻ đang dùng trộm token $\rightarrow$ Lập tức khóa toàn bộ phiên của tài khoản đó để bảo vệ người dùng!
3. **Mở rộng Đa thiết bị (Multi-Device Management):**
   - Giúp người dùng xem được danh sách thiết bị đang đăng nhập: *"Chrome trên Windows"*, *"iPhone 15 tại Hà Nội"* và có thể bấm đăng xuất từ xa từng thiết bị.

### 5. Ngữ cảnh Admin khóa tài khoản / Mất cắp điện thoại: "Hacker chính là nhân viên bị đuổi việc đúng không?"
**CHÍNH XÁC 100%!** Trong an toàn thông tin, đây là 2 mối nguy hiểm thực tế cực lớn:
- **Mối đe dọa nội bộ (Insider Threat):** Nhân viên bị sa thải trong ngày, ôm lòng bất mãn. Họ mở sẵn Postman hoặc còn lưu token trên máy tính cá nhân để lén xóa dữ liệu đơn hàng, hủy hợp đồng xe, hoặc tải toàn bộ danh sách CCCD và số điện thoại khách hàng đem bán.
- **Mất cắp thiết bị vật lý:** Nhân viên đi giao xe ngoài đường bị cướp giật điện thoại hoặc laptop. Kẻ trộm mở máy vào hệ thống thao túng.
- $\rightarrow$ Thao tác Admin bấm **"Khóa tài khoản"** hoặc **"Thu hồi phiên"** giúp server từ chối ngay lập tức mọi request mang token cũ, bảo vệ an toàn tuyệt đối cho tài sản của nhà xe!

---

### 6. Mẹo thực chiến kiểm tra Cookie / Token trên Chrome DevTools & Swagger
- **Tại sao Swagger UI không hiển thị Refresh Token trong Cookie?**
  - Vì Refresh Token được Backend bảo vệ bằng cờ `HttpOnly`. Javascript (bao gồm cả Swagger UI) bị trình duyệt cấm đọc Cookie này để chống tấn công XSS.
- **Tại sao khi gọi `/refresh-token` thấy Token cũ và mới trên DevTools giống hệt nhau?**
  - Tab **Application > Cookies** của Chrome DevTools là một **bản chụp tĩnh (Snapshot)**, nó **không tự động cập nhật** khi có API chạy ngầm trả về header `Set-Cookie`.
  - Để thấy token mới: Phải bấm nút **Reload (biểu tượng mũi tên xoay tròn ⟳)** ở góc trên tab Application, hoặc kiểm tra trực tiếp ở tab **Network > Response Headers > Set-Cookie**.

## PHẦN III: HIỆU NĂNG DATABASE: PHÂN TRANG PAGEABLE, INDEX & PARTITIONING

---

### 1. Cơ chế phân trang `Pageable` & `PageRequest`
#### a. Tại sao cứ truyền `Pageable` là Spring Data JPA tự phân trang?
- Khi khai báo:
  ```java
  Page<Booking> findByTenantId(UUID tenantId, Pageable pageable);
  ```
- Spring Data JPA sử dụng Reflection phân tích tham số `Pageable`. Nó tự động tách query thành **2 câu lệnh SQL riêng biệt** gửi xuống PostgreSQL:
  1. **Câu 1 (Lấy dữ liệu trang hiện tại):**
     ```sql
     SELECT * FROM bookings 
     WHERE tenant_id = ? 
     ORDER BY created_at DESC 
     LIMIT 20 OFFSET 40; -- Trang 3, mỗi trang 20 dòng
     ```
  2. **Câu 2 (Đếm tổng số bản ghi để tính số trang `totalPages`):**
     ```sql
     SELECT COUNT(*) FROM bookings WHERE tenant_id = ?;
     ```

#### b. Cạm bẫy Deep Paging (Khi dữ liệu lớn > 1.000.000 dòng)
- Khi người dùng nhảy tới trang thứ 10.000: `LIMIT 20 OFFSET 200000`.
- PostgreSQL bắt buộc phải quét và sắp xếp qua 200.000 dòng đầu tiên rồi mới vứt đi để lấy 20 dòng cuối cùng $\rightarrow$ Cực kỳ ngốn CPU và RAM.
- **Giải pháp tối ưu:** Dùng **Keyset Pagination (Cursor-based Pagination)**:
  ```sql
  SELECT * FROM bookings 
  WHERE tenant_id = ? AND id > :lastSeenId 
  ORDER BY id ASC 
  LIMIT 20;
  ```
  Nhảy trực tiếp đến vị trí ID tiếp theo dựa trên cây B-Tree của Index, tốc độ luôn là $O(1)$ dù dữ liệu có hàng chục triệu dòng.

---

### 2. Khi Database đã đánh Index, câu lệnh `SELECT` có luôn tự động dùng Index không?
**HOÀN TOÀN KHÔNG!**  
PostgreSQL có bộ não **Query Planner**. Trước khi chạy câu query, nó tính toán chi phí (Cost) và sẽ **CỐ TÌNH BỎ QUA INDEX** trong 5 trường hợp sau:

| Trường hợp bỏ qua Index | Ví dụ code gây lỗi | Cách khắc phục chuẩn |
| :--- | :--- | :--- |
| **1. Bảng quá ít dữ liệu** | Bảng `roles` chỉ có 5 dòng | Không cần sửa (quét toàn bảng còn nhanh hơn tra cây Index). |
| **2. Dùng hàm bọc trên cột Index** | `WHERE LOWER(email) = 'abc@gmail.com'` | Đánh Expression Index: `CREATE INDEX idx_user_lower_email ON users(LOWER(email));` |
| **3. Bọc hàm trên cột ngày tháng** | `WHERE DATE(created_at) = '2026-10-22'` | Dùng khoảng Range: `WHERE created_at >= '2026-10-22' AND created_at < '2026-10-23'` |
| **4. Ký tự đại diện `%` ở đầu** | `WHERE full_name LIKE '%Hieu'` | B-Tree chỉ tìm từ trái sang. Chuyển thành: `WHERE full_name LIKE 'Hieu%'` (hoặc dùng Trigram Index). |
| **5. Vi phạm Left-most Prefix** | Index là `(tenant_id, status)` nhưng query lại viết `WHERE status = 'ACTIVE'` | Composite Index bắt buộc phải có cột đầu tiên bên trái (`tenant_id`). |

> 🛠️ **Công cụ kiểm tra bắt buộc:** Thêm `EXPLAIN ANALYZE` vào đầu câu SQL trên DBeaver / pgAdmin. Nếu thấy `Index Scan` là thành công; nếu thấy `Seq Scan` (Sequential Scan) là đang bị quét toàn bảng!

---

### 3. Chiến lược đánh Composite Index cho Car Rental SaaS
Mọi bảng nghiệp vụ trong kiến trúc Multi-tenant đều có điều kiện tiên quyết là `tenant_id`. Do đó, cần đánh các chỉ mục đa cột (Composite Index) chuẩn:
```sql
-- Tối ưu cho màn hình danh sách Booking lọc theo trạng thái và ngày tạo
CREATE INDEX idx_bookings_tenant_status_created 
ON bookings(tenant_id, status, created_at DESC);

-- Tối ưu cho màn hình tra cứu xe sẵn sàng (available) theo chi nhánh
CREATE INDEX idx_vehicles_tenant_branch_status 
ON vehicles(tenant_id, branch_id, status);
```

---

### 4. Cơ chế Partitioning (Phân vùng bảng) trong Database
- **Bản chất:** Là việc chia một bảng khổng lồ (vài chục triệu bản ghi) thành nhiều bảng vật lý nhỏ hơn nằm bên dưới, trong khi ứng dụng vẫn nhìn thấy một bảng duy nhất.
- **Hai hình thức phổ biến:**
  1. **Range Partitioning (Theo dải thời gian):** Bảng `bookings_2025`, `bookings_2026`, `bookings_2027`. Khi tìm kiếm đơn hàng năm 2026, PostgreSQL tự động loại bỏ việc quét các bảng của năm khác (**Partition Pruning**).
  2. **List Partitioning (Theo Tenant):** Phù hợp với các khách hàng Enterprise VIP cần phân tách dữ liệu vật lý riêng biệt.
- **Định hướng Car Rental:** Giai đoạn MVP dữ liệu chưa đủ lớn thì chỉ cần đánh tốt **Composite Index**. Khi một nhà xe đạt trên 5 triệu đơn đặt xe mới bắt đầu áp dụng Partitioning theo năm.

### 1. Dựng HashiCorp Vault trong Docker
- **Mục tiêu:** Không lưu bất kỳ mật khẩu Database, secret key JWT, hay API key nào trong code Git hoặc file `application.yml`.
- **Mô hình hoạt động:**
  ```
  [ Spring Boot Startup ] ──> Kết nối HashiCorp Vault Container (Port 8200)
                                      │
                                      ▼
                        Vault cấp Secret vào Bộ nhớ RAM
                                      │
                                      ▼
             Spring Boot dùng mật khẩu trong RAM để mở Database Connection
  ```
- **Lộ trình:** Dev sẽ tự nghiên cứu và cấu hình dịch vụ Vault trong file `docker-compose.yml`, sau đó tích hợp thư viện `spring-cloud-starter-vault-config` khi chuẩn bị môi trường Staging/Production.

---

### 2. Định hướng SSO (Single Sign-On) & BAM
- **SSO (VNPAY ID / OIDC):** Cho phép người dùng đăng nhập bằng tài khoản nội bộ tập trung. Hệ thống tuân thủ chuẩn OAuth2 / OpenID Connect với luồng Authorization Code Flow kết hợp PKCE.
- **BAM (Business Account Management):** Cổng quản lý tài khoản doanh nghiệp. Sau khi hệ thống vận hành trơn tru luồng cốt lõi, sẽ bổ sung Adapter để ánh xạ (map) quyền hạn từ BAM về hệ thống SaaS.

---

### 3. Dynamic RBAC (Quyền động quản lý qua API)
- **Yêu cầu của Lead:** Không hardcode quyền trong Enum Java (vì mỗi nhà xe lại muốn phân quyền cho nhân viên theo cách riêng).
- **Thiết kế đã có:** Hệ thống đã chuẩn bị sẵn các bảng `roles`, `permissions`, `role_permissions` trong PostgreSQL.
- **Kế hoạch:** Xây dựng bộ REST API CRUD Roles để Quản trị viên của từng nhà xe có thể tự tạo nhóm quyền (ví dụ: "Nhân viên rửa xe", "Kế toán chi nhánh") và tích chọn các quyền tương ứng ngay trên giao diện web.
