## 1. Overview
The Account Management module provides Tenant Administrators with the capability to manage users (staff and sales agents), assign them to branches, swap their roles, and lock/unlock accounts. It enforces strict multi-tenant isolation (via PostgreSQL Row-Level Security) and branch-level scoping (via application security filters) to control access to booking creation, vehicle handovers, and return operations.

## 2. Requirements

### 2.1 Functional Requirements
1. **Account Management Access Restriction**: All account management functions (listing, inviting, editing, role swapping, locking/unlocking) are strictly restricted to the `TENANT_ADMIN` (and `SUPER_ADMIN`) role. Attempts by `STAFF` or `SALE` to access these endpoints will be rejected with a `403 Forbidden` response.
2. **Account Directory**: List, search, filter, and paginate accounts (users) belonging to the current tenant.
3. **Account CRUD Operations**:
   - **Create Account**: Invite/create a new user, associate them with the tenant, assign their role (`STAFF` or `SALE`), and map them to initial branches.
   - **Edit Account**: Update personal details (full name, phone, avatar) and edit system association (assigned branches).
   - **Assign & Switch Roles**: Change a user's role from `SALE` to `STAFF` or from `STAFF` to `SALE` dynamically.
   - **Lock/Unlock Account**: Toggle the active status (`is_active`) of a user within the tenant.
4. **Multi-tenant Role-Based Access Control**:
   - Enforce distinct permission boundaries for `TENANT_ADMIN`, `STAFF`, and `SALE` (no `BRANCH_MANAGER` role).
   - Prevent cross-tenant operations.
   - Prevent cross-branch operations for branch-restricted roles (`STAFF`, `SALE`).

### 2.2 Role & Permission Boundary Definition
- **TENANT_ADMIN (Business Owner) [Code: 1]**:
  - Scope: Tenant-wide (all branches).
  - Permissions: Complete CRUD on accounts, branches, vehicles, and bookings. Can execute all booking transitions (Create, Handover, Return).
- **STAFF (Operational Staff) [Code: 2]**:
  - Scope: Assigned branches only (via `user_branches` association).
  - Permissions: Read/write vehicles and bookings in assigned branches. Can execute all booking transitions (Create, Handover, Return) inside their assigned branches.
- **SALE (Sales Agent) [Code: 3]**:
  - Scope: Assigned branches only (via `user_branches` association).
  - Permissions: Can search vehicle availability and **create bookings** (`POST /bookings`) for their assigned branches.
  - **Restriction**: Forbidden from performing car handover (`POST /bookings/{id}/handover`) or vehicle return (`POST /bookings/{id}/return`).

### Key Schema Configurations:
1. **`user_tenants` Role Constraint**: Restricts role assignments exclusively to: `1` (TENANT_ADMIN), `2` (STAFF), and `3` (SALE).
2. **`bookings` Table Audit Fields & Status**:
   - `status SMALLINT` restricts booking status exclusively to: `1` (PENDING_HANDOVER), `2` (HANDED_OVER), `3` (RETURNED), and `4` (CANCELLED).
   - `handover_by UUID` referencing `user_tenants(user_id, tenant_id)` to track who performed the handover.
   - `returned_by UUID` referencing `user_tenants(user_id, tenant_id)` to track who received the vehicle back.
   - Indexes `idx_bookings_tenant_handover_by` and `idx_bookings_tenant_returned_by` have been defined to enable fast query lookups.

## 4. Technical Design

### 4.1 Account Operations Sequence Flow
1. **Search/List**:
   - Endpoint: `GET /api/v1/accounts`
   - SQL Logic:
     ```sql
     SELECT u.*, ut.role, ARRAY_AGG(ub.branch_id) as branch_ids
     FROM users u
     JOIN user_tenants ut ON u.id = ut.user_id
     LEFT JOIN user_branches ub ON u.id = ub.user_id AND ut.tenant_id = ub.tenant_id
     WHERE ut.tenant_id = :current_tenant_id
     GROUP BY u.id, ut.role;
     ```
2. **Role & Branch Assignment Swap**:
    - Endpoint: `PUT /api/v1/accounts/{id}/role`
    - Body: `{ "role": 2 | 3, "branchIds": ["uuid-1", "uuid-2"] }`
    - Authorization: Restricted to `TENANT_ADMIN`.
    - Business Logic:
      - Verify target user belongs to the same tenant.
      - Update the user's role in the `user_tenants` table.
      - Clear existing records in `user_branches` for this user and tenant, and insert the new associations.
3. **Lock/Unlock**:
    - Endpoint: `PATCH /api/v1/accounts/{id}/status`
    - Body: `{ "isActive": boolean }`
   - Authorization: Restricted to `TENANT_ADMIN`.
   - Business Logic:
     - Check if target user is not the current user (cannot lock self).
     - Update the target user's active status. (Optionally deactivates `user_tenants.is_active` if tenant-specific lock is needed; if system-wide lock is desired, updates `users.is_active`). For safety, we toggle `users.is_active` or soft-lock the tenant link. Let's toggle `users.is_active` as configured.

### 4.2 Security & ABAC Filter
When a user attempts booking operations, the backend validates their permissions at the service level:

```java
public void validateBookingOperation(Booking booking, UserPrincipal currentUser, OperationType opType) {
    if (currentUser.isSuperAdmin()) return; // Bypass

    UUID userTenantId = currentUser.getTenantId();
    if (!booking.getTenantId().equals(userTenantId)) {
        throw new AccessDeniedException("Tenant mismatch.");
    }

    int role = currentUser.getRole(); // 1: TENANT_ADMIN, 2: STAFF, 3: SALE
    
    // 1. Check Role Restrictions for Handover/Return
    if (role == 3 && (opType == OperationType.HANDOVER || opType == OperationType.RETURN)) {
        throw new AccessDeniedException("Sales agents are not authorized to perform handovers or returns.");
    }

    // 2. Check Branch Restrictions
    if (role != 1) {
        List<UUID> assignedBranches = currentUser.getBranchIds();
        if (!assignedBranches.contains(booking.getBranchId())) {
            throw new AccessDeniedException("Operation restricted to assigned branches only.");
        }
    }
}
```

## 5. Verification Plan

### 5.1 Test Cases & Scenarios
- **TC-01: List Accounts (Tenant Admin)**: Should return all accounts belonging to the current tenant, correctly showing their roles and assigned branches. Should NOT return accounts from other tenants.
- **TC-02: List Accounts (Staff/Sale)**: Should block access (only Tenant Admin can manage accounts).
- **TC-03: Create Booking (Sale in Assigned Branch)**: Should successfully create booking and set `created_by` to the sale agent's user ID.
- **TC-04: Create Booking (Sale in Unassigned Branch)**: Should deny booking creation (403 Forbidden).
- **TC-05: Handover booking (Sale)**: Attempting to call the handover endpoint as a Sale agent should immediately fail with 403 Forbidden.
- **TC-06: Handover booking (Staff in Assigned Branch)**: Should succeed, setting `handover_by` to the staff's user ID and status to `2` (`HANDED_OVER`).
- **TC-07: Lock User Account**: Deactivating a user should immediately reject any new login attempts or API calls under that user's session.
