# 1. Context

**Problem:**
Tenant Administrators currently lack the ability to add new employee accounts (Staff and Sale agents) directly within their tenant organization. This plan implements a secure, validated `POST /api/v1/accounts` API endpoint that enforces multi-tenant boundaries and role-specific branch assignment rules.

**Affected Modules:**
- `com.carrental.auth` - Handles DTO validation, REST controller mapping, and service execution for accounts.
- `com.carrental.branch` - Validates branch ownership during account creation.
- `com.carrental.security` - Encodes the account password.

**Non-Goals:**
- Allowing creation of `TENANT_ADMIN` or `SUPER_ADMIN` accounts.
- Changing passwords of existing users who are linked to the tenant.
- Changing user profiles (fullName/phone) of existing users who are linked to the tenant (only their role and branches are assigned).

**Language:** Java 17 (Spring Boot)
**Architecture:** REST Controller $\rightarrow$ Service $\rightarrow$ Repository (Existing layered structure)

**Rules:**
- Do NOT modify unrelated modules.
- Do NOT introduce new external dependencies.
- Validate that all database writes are encapsulated in a transactional block to prevent partial states.

**Performance Budgets:**
- API response latency: < 150ms (p95)

# 3. Conventions

**Naming:**
- Classes: `PascalCase` (e.g. `CreateAccountRequestDTO`)
- Methods/variables: `camelCase` (e.g. `createAccount()`, `existingUserOpt`)
- Constants: `UPPER_SNAKE_CASE`

**Error Handling:**
- Validation errors are handled automatically by `@jakarta.validation.Valid` in spring-web, throwing `MethodArgumentNotValidException` (returns 400 Bad Request via `GlobalExceptionHandler`).
- Business logic violations must throw `BadRequestException` (returns 400 Bad Request) or `TenantAccessDeniedException` (returns 403 Forbidden).

**Logging:**
- Library: SLF4J
- Log entry and exit at the service layer. Log warning/error reasons when checking constraints.

**Testing:**
- Framework: JUnit 5, Mockito, MockMvc
- Conventions: `AAA` (Arrange -> Act -> Assert) structure, separate unit tests for service layer and integration tests for controller layer.

# 4. Contracts

## Shared DTOs

### Request DTO: `CreateAccountRequestDTO`
```java
package com.carrental.auth.dto;

import jakarta.validation.constraints.*;
import java.util.List;
import java.util.UUID;

public class CreateAccountRequestDTO {
    @NotBlank(message = "Email must not be blank")
    @Email(message = "Invalid email format")
    private String email;

    @NotBlank(message = "Password must not be blank")
    @Pattern(
        regexp = "^(?=.*[a-zA-Z])(?=.*\\d).{8,}$",
        message = "Password must be at least 8 characters and contain both letters and numbers"
    )
    private String password;

    @NotBlank(message = "Full name must not be blank")
    private String fullName;

    @NotBlank(message = "Phone number must not be blank")
    @Pattern(
        regexp = "^0\\d{9,10}$",
        message = "Phone number must start with 0, contain only digits, and be 10 or 11 characters long"
    )
    private String phone;

    @NotNull(message = "Role must not be null")
    @Min(value = 2, message = "Role must be 2 (STAFF) or 3 (SALE)")
    @Max(value = 3, message = "Role must be 2 (STAFF) or 3 (SALE)")
    private Integer role;

    private List<UUID> branchIds;

    // Constructors, Getters, and Setters
}
```

# 5. Target Architecture

**Components:**
- `AccountController` - Handles REST mappings and extracts tenant context.
- `AccountManagementService` - Processes validation and creates database entities in a transaction.
- `PasswordService` - Hashes new user passwords.
- `UserRepository`, `UserTenantRepository`, `UserBranchRepository` - Database interfaces.

**Interaction Flow:**
```text
Client (Tenant Admin)
  -> POST /api/v1/accounts (with CreateAccountRequestDTO)
    -> AccountController.createAccount(request)
      - Retrieves tenantId from TenantContext.getTenantId()
      -> AccountManagementService.createAccount(tenantId, request)
        - Validates role vs branchIds constraint
        - Validates branch ownership via BranchRepository
        - Checks if email exists globally:
          - If exists:
            - Checks if UserTenant mapping exists -> throws BadRequestException if so.
            - If not, skips User creation/password hashing, directly maps UserTenant & UserBranch.
          - If new:
            - Hashes password via PasswordService
            - Saves User entity
            - Maps UserTenant
            - Maps UserBranch (if STAFF)
      <- Returns 201 Created with AccountResponseDTO
```

## TASK-002: Service Layer Implementation
**Phase/Sprint:** Phase 2
**Description:** Implement `createAccount` method in `AccountManagementService` containing all validation logic, transaction handling, and user/tenant/branch persistence.

**Input:**
- From TASK-001: `CreateAccountRequestDTO`

**Output:**
- New transaction-safe account mapping logic.

**Files:**
- `backend/src/main/java/com/carrental/auth/service/AccountManagementService.java` - **modify**: Inject `PasswordService` and add the `@Transactional` `createAccount(UUID tenantId, CreateAccountRequestDTO request)` method.

**Responsibilities:**
- De-duplicate `branchIds`.
- Check if role is `STAFF (2)`: validate that `branchIds` is not empty.
- Check if role is `SALE (3)`: validate that `branchIds` is empty/null.
- Validate that all `branchIds` belong to the given `tenantId`.
- Search user by email globally:
  - If exists, verify they aren't already in the current tenant, then link them.
  - If new, encode password, save user, map tenant, and map branches (for STAFF).
- Return populated `AccountResponseDTO`.

**Acceptance Criteria:**
- Creating a Staff with empty branch list throws `BadRequestException`.
- Creating a Sale with a non-empty branch list throws `BadRequestException`.
- Linking an existing user who is already in the tenant throws `BadRequestException`.
- Assigning branches belonging to another tenant throws `TenantAccessDeniedException`.

# 9. Edge Cases

| # | Scenario | Expected Behavior | Handled In |
|---|----------|-------------------|------------|
| 1 | Creator does not have `TENANT_ADMIN` role | Spring Security blocks the request and returns 403 Forbidden | TASK-004 |
| 2 | Invalid email format | Validation handler rejects with 400 Bad Request | TASK-001 |
| 3 | Password lacks letters or numbers | Validation handler rejects with 400 Bad Request | TASK-001 |
| 4 | Phone number does not start with 0 or has invalid length | Validation handler rejects with 400 Bad Request | TASK-001 |
| 5 | Role value is 1 (`TENANT_ADMIN`) or out of range [2, 3] | Validation handler rejects with 400 Bad Request | TASK-001 |
| 6 | STAFF account created with empty branch list | Service throws `BadRequestException` (returns 400) | TASK-002 |
| 7 | SALE account created with branch list items | Service throws `BadRequestException` (returns 400) | TASK-002 |
| 8 | Email already exists and belongs to the current tenant | Service throws `BadRequestException` (returns 400) | TASK-002 |
| 9 | Email already exists and belongs to another tenant | Service skips user creation and password hashing, links existing user to tenant and branches | TASK-002 |
| 10 | Branch IDs in request list belong to another tenant | Service throws `TenantAccessDeniedException` (returns 403) | TASK-002 |
| 11 | Duplicate branch IDs in request payload | Automatically distinct/de-duplicated before validation and mapping | TASK-002 |
| MT-1 | User A requests resource owned by User B (IDOR) | Inherently protected as we check tenant context on all operations | TASK-002 |
| MT-2 | Request missing tenant context | Service or controller rejects with 400 Bad Request | TASK-004 |
| MT-4 | Tenant ID in URL path differs from auth token tenant | N/A (Tenant ID is read directly from context, not paths) | TASK-004 |
