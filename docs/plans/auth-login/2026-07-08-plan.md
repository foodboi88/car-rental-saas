# 1. Context

**Problem:**
The Car Rental SaaS application needs a backend API codebase. We must initialize a Spring Boot backend and implement a secure, multi-tenant authentication system where users can belong to multiple tenants and select their working tenant, logging in with appropriate role-based privileges (`SUPER_ADMIN`, `TENANT_ADMIN`, `BRANCH_MANAGER`, `STAFF`).

**Affected Modules:**
- `backend/` (New directory containing the entire Spring Boot backend codebase).

**Non-Goals:**
- Implementing the frontend Next.js application.
- Implementing vehicles, customers, bookings, payments, pricing, or reports business services (beyond defining placeholder/scaffold entities if required for mapping user relationships).
- Multi-instance session replication (Redis token repository) — an in-memory token storage/blacklist will be used for MVP.

---

# 2. Constraints

**Language:** Java 17, Spring Boot 3.3.x, Spring Security 6.3.x
**Architecture:** Layered Architecture (Controller -> Service -> Repository -> Entity) with ThreadLocal TenantContext filter.

**Rules:**
- All new directories and code files must reside under `backend/`.
- No new maven dependencies should be added unless they are standard Spring Boot starters or standard JWT libraries (`jjwt-api`, `jjwt-impl`, `jjwt-jackson`).
- Enforce strict database column indexing for lookup performance.

**Performance Budgets:**
- Password Hashing: BCrypt strength 12 (approx. 100-150ms per hash).
- JWT Token Validation: < 5ms processing time per request.
- Auth API endpoints: < 200ms (p95) latency budget.

# 3. Conventions

**Naming:**
- Classes: `PascalCase` (e.g. `SecurityConfig`, `JwtAuthenticationFilter`, `AuthService`).
- Methods/variables: `camelCase` (e.g. `generateToken()`, `tenantId`).
- Constants: `UPPER_SNAKE_CASE` (e.g. `JWT_EXPIRATION_MS`).
- Packages: `com.carrental.<module>.<layer>` (e.g., `com.carrental.auth.controller`, `com.carrental.security`).

**Error Handling:**
- Restful API errors should return a standard `ApiResponse<T>` with HTTP status codes.
- Throw custom runtime exceptions (e.g., `ResourceNotFoundException`, `TenantAccessDeniedException`) and handle them globally in a `@ControllerAdvice` handler.
- Do not leak security-sensitive details in exception messages (return generic "Bad credentials" for all login failures).

**Logging:**
- Library: SLF4J (backed by Logback, standard in Spring Boot).
- Format: Standard console output.
- Required at: Filter entry points, user authentication success/failure, tenant selection changes, token refresh failures, and global controller exceptions.

**Testing:**
- Framework: JUnit 5, AssertJ, Mockito, and Spring Boot Test MockMvc.
- Naming: `should_[ExpectedBehavior]_when_[Scenario]` (e.g., `should_return_401_when_password_incorrect`).
- Coverage: > 80% coverage for all security utility classes and services.

**Task Size:**
- Max 200 LOC per task excluding tests. Split if larger.

# 4. Contracts

## Interface: `com.carrental.security.JwtTokenProvider`
```text
generateAccessToken(user: User, tenantId: UUID, role: String, branchIds: List<UUID>): String
  - pre: user must not be null
  - post: returns a signed HS256 JWT access token with 15-minute expiration containing claims: email, tenant_id, role, branch_ids.
  
generateRefreshToken(user: User): String
  - pre: user must not be null
  - post: returns a signed HS256 JWT refresh token with 7-day expiration containing: sub (user_id), jti, type=refresh.

validateToken(token: String): boolean
  - pre: token must not be null
  - post: returns true if token signature is valid, token type matches, and is not expired; otherwise returns false.

getClaims(token: String): Claims
  - pre: token is non-empty and validated
  - post: returns all JWT claims parsed from the token.
```

## Interface: `com.carrental.auth.service.AuthService`
```text
login(request: LoginRequest): LoginResponse
  - pre: request.email and request.password are non-empty
  - post: if credentials are correct and user has exactly 1 tenant or is super admin, returns tokens and requiresTenantSelection = false. If user has multiple tenants, returns tenant options and requiresTenantSelection = true.
  - throws: BadCredentialsException when email/password wrong, DisabledException when user is inactive.

selectTenant(request: SelectTenantRequest, userId: UUID): LoginResponse
  - pre: request.tenantId is not null, user belongs to this tenant in user_tenants
  - post: returns final LoginResponse with access and refresh tokens.
  - throws: AccessDeniedException if user does not belong to the tenant.
```

# 5. Target Architecture

**Components:**
- `AuthController` - REST Endpoint Layer exposing `/api/v1/auth/login`, `/api/v1/auth/select-tenant`, and `/api/v1/auth/refresh`.
- `AuthService` - Coordinates login credentials verification, tenant resolutions, and token provisioning.
- `JwtAuthenticationFilter` - Intercepts requests, validates JWT, populates SecurityContext and `TenantContext` ThreadLocal variables.
- `TenantContext` - Thread-local storage for current request scoping.
- `Flyway` - Manages database structure and seeds initial test data.

**Interaction Flow:**
```text
Client
  -> AuthController.login(LoginRequest)
    -> AuthService.login(email, password)
      -> UserRepository.findByEmail(email) -> User
      -> PasswordService.matches(password, hash) -> true
      -> UserTenantRepository.findAllByUserId(userId) -> List<UserTenant>
      (Case: 1 Tenant)
      -> JwtTokenProvider.generateAccessToken(user, tenantId, role, branchIds) -> jwt
      -> JwtTokenProvider.generateRefreshToken(user) -> refresh_token
    <- returns LoginResponse(jwt, requiresTenantSelection=false, user, selectedTenant) + Cookie(refresh_token)
```

**Key Decisions:**
- **In-Memory Revocation**: For simplicity and testability in Phase 1 (MVP), token revocation checks will be run via an in-memory registry (`ConcurrentHashMap` in `TokenService`) instead of requiring Redis, since Redis is designated as Phase 2.
- **BCrypt cost factor 12**: Chosen to balance security against brute-force attacks and CPU latency during login requests.
